## 2026-11-24 的断开期间更新候选

用户调整顺序为“关闭 → 在断开情况下更新 → 恢复”，并选择 30 秒固定更新窗口。
旧实现运行新增的三个测试方法均失败：更新实际发生在连接后，未检查按需连接，
更新期间的意外重连也未报错。实现先保留不用开关 URL 的防护，再增加：

- 明确要求按需连接关闭；开启、缺失、重复、读取失败或格式未知时不停止 VPN。
- 激活应用并确认前台；停止后确认 Disconnected 才请求更新。
- 30 秒窗口内检查 VPN 及前台状态；意外变化或中断会结束等待并尝试恢复。
- 停止失败或未断开时不更新，但仍发送恢复请求；更新失败也不跳过恢复。
- AppKit 检查只认可当前处理程序的可见、活跃、未退出实例，激活确认有明确时限。
- 原有延迟关闭 URL 场景继续保留，确认源码不会重新产生这类请求。

隔离测试通过命令替身记录更新时的连接状态和模拟时钟，验证 start 不早于

- 更新失败且改变连接状态时仍恢复；额外启动最多两次，不重复停止。

## 历史 Issue #1 的两次开启验证（2026-11-03）

先添加两项测试，在原实现上均失败：缺少第二次 `on`，也没有相应的调用记录。
加入有限重发后，全量 22 项测试通过。新增覆盖：

- 模拟首次 `on` 返回 0 但没有产生连接效果；仍在 10 秒延时后发出第二次 `on`。
- 第一次失败、第二次失败及两次都失败时，仍完成剩余更新与隐藏动作。
- 两次调用各自包含尝试序号；任何失败保持最终非零退出码。
- 完整调用轨迹仅含一次关闭、两次开启、一次更新和一次隐藏；固定等待共 25 秒。
- 各个 URL 失败和全部失败时仍遵守次数限制与执行顺序。

测试中的连接效果是替身状态，用于模拟调用成功但没有效果的情形，
不是对真实 Loon、网络或故障根因的验证。详见 [影响记录](impact/retry-on-dispatch.md)。
