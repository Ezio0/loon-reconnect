# 开启请求的有限延迟重发

## 问题与证据

[Issue #1](https://github.com/Ezio0/loon-reconnect/issues/1) 记录了一次定时重连后 VPN
没有恢复的故障：`loon://on` 调用返回成功，随后订阅更新调用报 `-1712`，
单独补发一次 `on` 后观察到连接恢复。

现有证据不能确定断连原因，也不能证明 `-j` 或订阅更新导致断连。
`open` 成功只代表 URL 已发出；只在命令报错时重试会漏掉本次这种情况。
本次按既有重连流程的缺陷修复处理，保留 Impact 和回归测试。

## 修复范围

- 每轮仍只发送一次 `off`，等待 3 秒后发送第一次 `on`。
- 不论第一次调用返回成功或失败，等待 10 秒后再发送一次 `on`。
- 每轮总共两次 `on`，第二次后等待 10 秒，再请求一次订阅更新。
- 两次 `on` 的成功与失败日志均标记 `attempt 1/2` 或 `attempt 2/2`。
- 任一调用失败仍使本轮返回非零；后续调用成功不抹去前面的错误。
- 保留 `open -g -j`，以及更新请求后等待 2 秒并隐藏窗口的逻辑。
- 不增加 VPN 状态或网络探测；不改变 6 小时默认周期、加载行为和安装路径。

完整顺序为：

```text
off → 等待 3 秒 → on（1/2）→ 等待 10 秒 → on（2/2）→ 等待 10 秒
    → 更新全部订阅 → 等待 2 秒 → 隐藏 Loon
```

选择一次额外重发，是为首次请求未生效留出第二次机会，并限制命令数量。
不重发 `off`，避免为重试再次断开；不重发订阅更新，避免重复下载。
这是降低单次开启请求未生效风险的措施，不能保证 Loon 恢复连接。

## 影响与边界

正常流程固定等待共 25 秒，比原流程多 10 秒；命令调用和隐藏确认另需时间。
管理工具与 README 中查看日志的等待提示同步调整为约 30–40 秒，调用超时可能更久。
调度配置与隐藏实现保持不变，已有用户需要升级安装副本才会采用新流程。

修改文件限定为运行脚本、管理工具的等待提示、命令替身和回归测试、README、
本影响记录及验证记录。不会添加依赖或安装新的系统服务。

## 验证与交付

- 先补充可失败的回归测试：首次开启返回成功却未生效时仍有第二次调用；
  首次失败或第二次失败时仍继续更新、隐藏，并保留非零退出码。
- 使用模拟系统命令检查完整顺序、固定延时、调用次数与日志，不操作真实 VPN。
- 执行全量隔离测试、两份 Shell 的语法检查，以及差异和仓库卫生检查。
- 本次没有稳定的实机复现，隔离测试通过不能证明实际故障已消除。
- 验证完成后，用户已明确授权本机部署、提交并推送 GitHub。
  本机已先备份旧脚本和配置，再原子替换运行脚本；不重载任务，不主动触发真实重连。

## 依据

[Loon 官方 URL Scheme](https://nsloon.app/docs/Scheme/) 分别定义 `on` 为开启 VPN、
`off` 为关闭 VPN。重复请求使用 `on`，不使用切换开关状态的接口。
