# 使用系统接口控制 VPN 开关

本记录对应已实测的先发送开启请求、后更新版本。用户曾要求断开期间更新，
产生了 [另一候选](update-while-disconnected.md)，但随后允许连接状态更新并要求再测当前版本。
2026-11-26 发布前已将仓库源码对齐本机采用的版本，另一候选单独保留本地归档。
本工具不修改按需连接；本机保持开启，也未部署另一候选。

## 复发证据与判断

2026-11-24，用户报告早上约 9 点打开 Loon 时看到 VPN 开关关闭，随后手动开启。
安装副本与已发布的 `d4e004e` 运行脚本一致，任务仍每 21600 秒执行。
只读检查发现以下事件，时间均为 Asia/Shanghai：

- 04:27 的关闭、两次开启、订阅更新 URL 全部超时，返回 Apple Event 错误 `-1712`。
- 04:27:40，脚本读取的系统 VPN 状态为 `Connected`，因此没有调用系统恢复。
- 09:15:05，Loon 主应用从挂起恢复，随后收到两条 `GURL/GURL` Apple Event。
- 09:15:06，主应用处理 `UISOpenURLAction`，接着向系统发出停止 Loon VPN 的命令；
  系统状态确实变为 `Disconnected`。
- 09:15:45，Loon 发出开启命令，09:15:46 系统恢复为 `Connected`。
- 10:27 的下一轮自动任务完成四次 URL 调用、连接确认和窗口隐藏，没有报错。

现有日志支持“应用恢复后才处理旧 URL，导致延迟关闭”的判断，但没有记录 URL 内容，
也无法把早上的事件标识直接对应到凌晨调用，因此不能将它写成已经证明的唯一根因。
这些证据也不能证明凌晨至早上一直断网，或者订阅更新本身关闭了 VPN。

已知的机制缺口是：Apple Event 超时并不保证请求已经取消，而流程末尾的一次
`Connected` 读取无法阻止关闭请求在脚本结束后才生效。增加 `on` 次数和允许激活
没有消除这个缺口。本次按既有故障的热修复处理，保留影响记录及隔离回归测试。

## 修复范围

- 通过实际 `loon://` 处理程序标识，匹配唯一启用的 VPN 服务；使用其 UUID 操作。
- 将原有的一次 URL 关闭、两次 URL 开启替换为 `scutil --nc stop/start`。
  启动请求直接交给系统 VPN 服务，不依赖 Loon 主应用接收开关 URL。
- 保留关闭后 3 秒、两次开启后各 10 秒的固定等待，以及每轮一次订阅更新。
- 仅订阅更新继续使用 `loon://update?sub=all`。不再发送 `loon://off` 或 `loon://on`。
- 保留更新后的连接状态确认、最多两次额外系统启动、过渡状态等待及窗口隐藏。
  日志区分固定的两次启动与额外恢复请求；任何命令错误保留最终非零退出码。
- 即使系统停止失败，也继续尝试开启；不通过再次关闭、强制退出或无限重试恢复。

默认 6 小时周期、登录时不执行、安装位置、任务标识和管理工具均不变。
不增加网站探测、唤醒触发或持续监控，不操作其他 VPN，不读取订阅和凭证。

## 已知限制

新版本不再产生开关 URL；它不能撤销旧版本可能已经投递的事件。
`scutil` 返回成功仅表示命令提交成功，仍以随后的系统状态确认结果为准。
主应用挂起时订阅更新仍可能超时或延后处理；此修复不声称解决所有 URL 派发故障。
`Connected` 只表示读取时系统认为隧道已连接，不能保证网站连通或未来持续连接。
